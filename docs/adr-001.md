# ADR-001: Notificación asíncrona con patrón Outbox en la misma transacción del evento

**Estado**: Aceptado
**Fecha**: 2026-10-28

## Contexto

El requisito más delicado del sistema es doble:

1. *Un evento de cambio de estado no puede perderse*: una vez aceptado, el cliente debe enterarse.
2. *El envío al webhook del cliente no debe bloquear la respuesta* del endpoint de registro,
   y ante fallo del webhook se reintenta (timeout de 5 s, espera creciente, hasta 5 intentos).

Cumplir ambos puntos con un solo mecanismo es la decisión de diseño de mayor impacto del sistema:
idempotencia, resiliencia y la demostración de notificaciones FAILED consultables dependen de él.

## Opciones evaluadas

| Opción | Comportamiento frente a los requisitos |
|---|---|
| **A. Envío sincrónico dentro del request** | Si el webhook tarda (hasta 5 s), `POST /v1/events` se bloquea. Si el proceso muere tras registrar el evento pero antes de enviar, el evento queda **sin notificar**: se pierde. |
| **B. Cola en memoria disparada tras el commit** | Respuesta inmediata correcta, pero el reinicio del proceso pierde la cola: eventos aceptados que jamás se notifican. |
| **C. Broker externo (Redis, SQS, Kafka)** | Solución canónica para volumen, pero añade una pieza infraestructural que `docker compose up` tendría que levantar y sostener. Coste operacional desproporcionado para el alcance. |
| **D. Outbox (BD + worker con polling)** | La notificación nace `PENDING` en la **misma transacción** que el evento. Tras el commit, un worker la despacha con backoff. Un crash jamás deja el sistema inconsistente: la fila pendiente sobrevive y se retoma. |

## Decisión

Opción **D — patrón Outbox**.

`RegistrarEventoDeEstadoUseCase` ejecuta bajo una transacción real de PostgreSQL. El caso de uso
depende del puerto `Transaccion`; el adaptador `TransaccionPostgres` la implementa abriendo una
transacción de Drizzle y exponiendo la conexión de esa transacción a los repositorios mediante un
proveedor — mientras dure la transacción, todo `INSERT` de repositorios ocurre dentro de ella:

```text
BEGIN
  INSERT INTO eventos_de_estado  (...)        ← UNIQUE (tenant_id, event_id) + ON CONFLICT DO NOTHING
  INSERT INTO notificaciones      (PENDING)
COMMIT  → 201 con el cuerpo de respuesta al emisor

worker (cada 2 s, batch 5, SELECT ... FOR UPDATE SKIP LOCKED):
  POST { evento } → webhook del tenant   (timeout 5 s, firma HMAC-SHA256)
    exito            → DELIVERED
    fallo            → reprograma para ahora + 2^(intento-1) * base
    5 intentos agotados → FAILED (consultable en GET /v1/notifications?status=FAILED)
```

## Consecuencias

A favor:

- No existe el estado intermedio "evento guardado, notificación de destino desconocida".
- El estado FAILED es consultable por HTTP: el ciclo de fallo queda observable sin herramientas externas.
- La política de reintentos vive en el dominio (`PoliticaDeReintentos`), testeada con tests unitarios puros sin base de datos ni red.
- Sin infraestructura adicional: PostgreSQL es también el sistema de localización de pendientes.

En contra / limitaciones aceptadas:

- La latencia de entrega queda ligada al intervalo de polling (2000 ms por defecto). Preferimos consistencia sobre latencia extrema.
- El polling procesa lotes de tamaño fijo. Con un volumen 10× mayor moveríamos a `LISTEN/NOTIFY` o un broker; queda anotado en el README.
- La idempotencia depende de la constraint `UNIQUE(tenant_id, event_id)` con `ON CONFLICT DO NOTHING`.
  Los tests de integración protegen esto explícitamente (doble inserción concurrente → una sola fila).

## Verificación

El ADR está demostrado por las pruebas de integración `tests/integration/notificacion/outbox-e2e.test.ts`
(contra PostgreSQL real vía testcontainers y un servidor HTTP real, sin mocks del webhook):

- Entrega feliz: evento aceptado → notificación `PENDING` en la BD (misma transacción) → worker →
  `POST` firmado con HMAC válido → estado `DELIVERED` con `entregadoEn`, consultable por API.
- Fallo del webhook: 5 intentos con backoff (1/2/4/8/16 s) → `FAILED` con `intentos=5` y el error
  del último intento, consultable en `GET /v1/notifications?status=FAILED` y sin más reintentos.
- Timeout del webhook cuenta como intento fallido y deja la notificación reprogramada.
- Tenant sin webhook configurado → `FAILED` con error descriptivo, sin llamar al despachador.
- Idempotencia de la constraint: doble inserción concurrente del mismo `(tenant_id, event_id)` →
  una sola fila.
